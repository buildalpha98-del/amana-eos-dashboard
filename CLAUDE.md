# Amana OSHC EOS Dashboard

## Project Overview
- **Product**: EOS (Entrepreneurial Operating System) management dashboard for Amana OSHC (Out of School Hours Care)
- **Stack**: Next.js 16, TypeScript, Prisma ORM 5.22, PostgreSQL, Tailwind CSS, Vercel
- **Auth**: NextAuth.js with credential-based login
- **Email**: TWO providers by design — Brevo for marketing/campaign sends (`src/lib/brevo.ts`), Resend for transactional/assignment (`src/lib/email.ts`, branded HTML templates). Events: `/api/webhooks/resend` AND `/api/webhooks/brevo` (Phase 3, `?secret=` auth via `BREVO_WEBHOOK_SECRET`) both write `EmailEvent`; Brevo events correlate to sends via `DeliveryLog.externalIdType` (`brevo_message` <50-recipient sends matched on message-id; `brevo_campaign` ≥50 matched on camp_id) → `EmailEvent.deliveryLogId`. Suppression (`EmailSuppression`) is enforced at EVERY send path via `getSuppressedEmails()` (batch) — campaign send, recipient-count, and the Resend wrapper; the webhook auto-suppresses on bounce/spam/unsubscribe/block. Test-send: `POST /api/email/test-send` (self-only, "[Test] " prefix, rate-limited 5/min). Creative-request assignment emails BYPASS the `shouldReceiveNudge` leadership gate on purpose (work-queue notification; the gate excludes marketing-role users) — see `send-assignment-email.ts`.
- **State**: React Query (TanStack Query) for server state
- **Markdown**: react-markdown + remark-gfm + rehype-sanitize (for report viewer)
- **PDF**: jsPDF (for branded report exports)

It deliberately does NOT run `prisma migrate deploy` — production migrations come from `vercel.json`'s `buildCommand`. Putting them in the npm script meant a local build pointed `migrate deploy` at the production DB, and broke CI's E2E job with P3005.

## Key Conventions
- Prisma schema changes: use `npx prisma migrate dev` for tracked migrations, `npx prisma db push` for quick dev iteration
- Cron jobs: Bearer CRON_SECRET auth via `verifyCronSecret`, idempotency via `acquireCronLock`
- API key auth: `authenticateApiKey(req, scope)` with scope-based access (for dashboard-generated keys)
- **Cowork API auth**: `authenticateCowork(req)` from `@/app/api/_lib/auth` — Bearer token vs `COWORK_API_KEY` env var. ALL cowork routes use this pattern (not `authenticateApiKey`).
- Dashboard API auth: `withApiAuth(handler, options?)` from `@/lib/server-auth` — session-based wrapper with rate limiting, timeout, and role/feature authorization
- Nav config: centralized in `src/lib/nav-config.ts` with sections (Home, EOS, Operations, Growth, People, Admin, Settings). Keep each section's items contiguous — the sidebar renders one header per section name (Marketing items live inside Growth as of 2026-07-12)
- **Curated sidebar** (2026-07-12): every nav item has a `core` tier — `true` (always visible), `Role[]` (visible by default for those roles; owner matches all), or omitted (behind the section's "+N more" toggle). The active page and badge-carrying items always surface; sections with ≤2 items skip curation. When adding a nav item, decide its tier — omitting `core` is a deliberate "overflow" choice, not a default to skip.
- Email templates: inline styles in `src/lib/email-templates.ts`, use `baseLayout()` wrapper and `buttonHtml()` for CTAs
- Vercel cron config in `vercel.json`
- Build command: `npm run build` — always verify after changes
- Toast system: `toast({ description: "..." })` — `description` is required, not optional
- **Meeting recorder v2 (2026-09-14)**: the MediaRecorder lives in `MeetingRecorderProvider` (mounted in the dashboard layout), NOT in the meeting page — v1 lost the first real L10 because any sidebar click unmounted it. Chunks persist to IndexedDB (`src/lib/recording-store.ts`) every 30 s; Stop / meeting completion / a dead mic end a session and upload through the unchanged `POST /api/meetings/[id]/recordings` path. Orphans surface via `RecordingRecoveryBanner`. `RecordingIndicator` is the always-visible REC pill. Never move recording state back below routing.

## Design System (2026-07-11)
- **Tokens only**: colors come from `src/app/globals.css` `@theme` — `text-foreground`/`text-muted`/`bg-card`/`bg-surface`/`bg-brand`/`border-border` etc. Never raw Tailwind grays, `bg-white`, or hex-in-className (ESLint warns via `design-token-rails`; `src/components/charts/` is exempt for Recharts). Translucent overlays on dark surfaces (`bg-white/10`) are fine.
- **`@theme` vs `@theme inline`**: colors/radii/shadows MUST live in plain `@theme` (a guard test enforces this). `inline` freezes utilities to literal values and silently breaks the `.dark { --color-* }` overrides and `[data-v2="staff"]` density overrides. Only the font tokens (which reference next/font vars) belong in `@theme inline`.
- **Dark mode**: driven by the `.dark` class on `<html>` + token overrides; `@custom-variant dark` is registered so `dark:` variants follow the app toggle, not the OS. For hardcoded tinted surfaces (amber banners, status-tinted rows), pair light classes with `dark:` variants (`bg-amber-50 dark:bg-amber-950/40`).
- **Buttons**: action buttons (primary/secondary/outline/ghost/destructive) use `Button` from `@/components/ui/Button` — never hand-roll `bg-brand text-white` / `bg-red-600` buttons. Tabs, sort headers, chips, and card-as-button wrappers stay raw, but icon-only buttons MUST have `aria-label`.
- **Page headers**: use `PageHeader` from `@/components/layout/PageHeader`; when it can't fit, canonical title classes are `text-xl font-heading font-semibold tracking-tight text-foreground` with `text-sm text-muted mt-1` description.
- **Micro text**: `text-2xs` (10px token) for badge/meta text — no arbitrary `text-[Npx]`.
- **Quarter strings (FINANCIAL YEAR as of 2026-07-28)**: EOS quarters follow the Australian FY (1 Jul – 30 Jun), NOT the calendar year. `Rock.quarter` format is `"Q1-FY27"` — Q1=Jul–Sep, Q2=Oct–Dec, Q3=Jan–Mar, Q4=Apr–Jun, with the FY named by its ENDING year. Always use `quarterLabel(date)` / `getCurrentQuarter()` / `shiftQuarter()` / `quarterDateRange()` / `compareQuartersDesc()` from `@/lib/utils`. Never hand-roll a quarter string or parse one with `.split("-")` + `Number()` — `Number("FY27")` is `NaN`, and hand-rolled variants have twice silently matched ZERO rocks (once via a space-separated `"Q3 2026"` in the L10 digest cron, once via calendar labels after the FY switch). `quarterDateRange()` exists because Q1 starts in JULY, so `(q-1)*3` month maths is wrong. Legacy calendar labels were migrated 1:1 by `20260728100000_rock_quarter_financial_year`; `calendarQuarterToFinancial()` implements the same remap if stale data resurfaces.

- **Per-send reports (Phase 4)**: `GET /api/email/reports/[deliveryLogId]` + `SendReportPanel` (opened from analytics recent sends). - **Attribution (Phase 5)**: `src/lib/campaign-attribution.ts` owns EVERY funnel query — window resolution (nullable campaign dates fall back to createdAt/now, clamped), attributed vs CONTEXTUAL counts (attributed = traced via `sourceActivation`/QR/tracked email; contextual = window+linked-services counts — never present contextual as attributed). Enrolments count `ParentEnquiryStageEvent` `toStage:"enrolled"` — EVERY stage write must go through `logEnquiryStageEvent` (ALL writers compliant as of 2026-08-08 — dashboard routes, cowork pipeline/stage, OWNA sync, VAPI, auto-cold cron; keep it that way for any new stage writer).
- **CSAT + guardrails (Phase 6)**: `CreativeRequestSatisfaction` — one 👍/👎 per delivered request, REQUESTER-only voice via `POST /api/creative-requests/[id]/satisfaction` (own endpoint — delivered is terminal and PATCH-locked); aggregates at `GET /api/marketing/creative-request-quality` (first-proof rate counts plain approvals ONLY; `approved_with_changes` stays denominator-only). **Frequency cap**: `MarketingSendRecipient` ledger — ALWAYS write via `recordMarketingSends()` (swallow-and-log; sources campaign/cowork/nurture/resend; test-send deliberately excluded), enforced by `getFrequencyCapped()` (3/rolling-7d) on BULK sends only (campaign + cowork; nurture/enquiry are recorded but never blocked); cowork sends are now suppression-filtered too (deliberate Phase 6 change); janitor prunes ledger rows >30d. **Cancel**: `POST /api/email/scheduled/[id]/cancel` — findUnique-first (legacy null externalIdType → 409), conditional claim `scheduled→cancelled`, then Brevo best-effort per type (`_sentMessageIds` captured on <50 sends for per-message cancel); local truth beats Brevo. **Re-send**: `POST /api/email/reports/[id]/resend` — partial rows only, suppression re-checked, cap NOT consulted, NEW DeliveryLog row cross-linked via `_resendOfDeliveryLogId`/`_resendDeliveryLogId` (double-retry 409s once stamped). Per-recipient dispatch machinery lives in `src/lib/email-dispatch.ts` (shared by send + resend).

## Staff Induction & Training LMS (hard-gated)
- **Gate is the point**: a new starter cannot be rostered or clock in until essential training is complete AND (for genuine new hires) a State Manager/Admin signs off their week-1 practical. Single source of truth: `src/lib/induction.ts` — `assertUserCleared(userId)` (throws `ApiError.forbidden`), `getInductionReadiness(userId)`, `recomputeInductionState`, `onModuleProgressed`. Pure edge-safe helpers (for middleware) in `src/lib/induction-lock.ts`.
- **Enforced at 7 surfaces**: roster shift create (`roster/shifts` POST) + reassign (`roster/shifts/[id]` PATCH) + open-shift claim, and all clock-ins: per-shift, auto, unscheduled, and kiosk. Each calls `assertUserCleared`.
- **State machine** on `User.inductionStatus` (`InductionStatus` enum): `new_starter → in_training → awaiting_signoff → cleared`. Migration default is `cleared` so deploy is a no-op. `inductionGraceUntil` (backfill grace), `inductionOverrideUntil` (audited admin override), `inductionDueDate`, `inductionClearedAt/ById`.
- **Locked-mode**: while `new_starter`/`in_training`-without-grace, middleware + Sidebar restrict the user to `/my-training`, `/learn`, `/profile`, `/handbook`, `/policies`, `/compliance`. Per-USER via JWT (`inductionStatus`/`inductionGraceUntil` on token, refreshed on the 5-min tokenVersion cadence) — NOT the per-role page-override system, and NOT a new Role enum value. ~5-min UI-lock lag is expected; the gate APIs read the DB live so clock-in is never stale.
- **Quiz engine**: `src/lib/quiz.ts` — deterministic seeded shuffle + server-side scoring (80% pass). Correct answers never sent to the client; the client submits DISPLAY indices mapped back via the per-attempt permutation (seed = enrollmentId+moduleId+attemptNumber). API: `GET/POST /api/lms/modules/[moduleId]/quiz` (start/submit — GET reuses an unsubmitted attempt rather than minting rows). Admin CRUD: `/api/lms/quiz-questions`. `LMSQuizQuestion` + `LMSQuizAttempt` (submittedAt marks in-progress vs submitted; `optionsFingerprint` is recorded at start and submit 409s if the question set changed mid-attempt). The submit payload carries exactly ONE answer index — `explanations[].correctIndex`, in DISPLAY space; never add a canonical-space index alongside it (that ambiguity caused the PR #202 bug).
- **Enrollment recompute**: `recalcEnrollmentStatus(enrollmentId)` in `src/lib/lms-progress.ts` is the ONLY place enrollment status is derived from module progress — used by quiz submit, `/api/lms/module-progress`, and `/api/lms/enrollments` progress mode. On completion it also writes `LMSEnrollment.score` (average of scored module progress) for the transcript PDF; don't reimplement this inline in routes.
- **Immersive player**: `/learn/[enrollmentId]` (route group OUTSIDE `(dashboard)`, opens in a new tab, no sidebar). Gated click-through — 60s dwell floor for reading modules, quiz-pass for quiz modules (`src/lib/course-player.ts`). Admins opening another learner's enrollment get a read-only preview (banner, free navigation, no auto-completion, no quiz attempts) — the write paths belong to the enrolled learner only. Rich media via a PLAYER-SCOPED sanitizer (`src/lib/lms-sanitize-schema.ts`): `<img>` Blob-host only, `<iframe>` YouTube/Loom/Vimeo only. NEVER apply this schema to ReportViewer/AiDraftReviewPanel/FloatingChatWidget (they keep the bare default).
- **Learner hub**: `/my-training` (Home nav, all roles). Admin surface: `/onboarding` → "Induction" tab (`InductionAdminTab`) — pipeline board, practical sign-off queue (signers = `head_office`/`admin`/`owner` only, no self-sign-off), annual training-calendar editor, backfill launcher.
- **Exempt roles** (`INDUCTION_EXEMPT_ROLES` in `src/lib/induction-lock.ts`): `owner`, `head_office`, `admin` (they administer the gate — locking them out deadlocks it) and `marketing` (no child-facing duties). The list governs locked-mode AND both auto-enrolment paths (`/api/induction/backfill`, `/api/cron/training-monthly`) — an exempt role enrolled by a cron would just be re-locked next sweep. `isInductionLocked(status, grace, { role, now })` takes an options object; `role` must be passed at every call site.
- **Gate satisfiability, part 2 (2026-09-17)**: a blocker's `href` pointing somewhere reachable is only HALF the invariant — something must also RE-EVALUATE the gate once the user resolves it. Recompute used to run only from `onModuleProgressed` (LMS progress) and course publishing, so the WWCC, policy and profile blockers could all be satisfied with nothing noticing; where no essential course was published there was no module to progress either, so there was no exit at all and real coordinators sat locked out of their own centre with a four-item sidebar. Every blocker-resolving route now calls `refreshInductionAfterBlockerChange(userId)` (swallow-and-log, null-tolerant for service-level certs): `compliance` POST, `policies/[id]/acknowledge`, `users/[id]/emergency-contacts`, `users/[id]/profile`, `users/[id]/avatar`. The registry test in `src/__tests__/api/induction-clear.test.ts` enumerates them — a NEW blocker needs a resolving route in that list.
- **The gate is inert without a curriculum (2026-09-19)**: `isInductionLocked` read STATUS alone, so locked-mode fired whether or not a single essential course was published — while `getInductionReadiness` counted published courses only and the rollout notes promised the gate "stays inert until courses are published". Amana's seeded essentials are DRAFTS, so real coordinators were held against a curriculum that did not exist: four sidebar items, no budget, no attendance, and nothing on `/my-training` they could finish. `isInductionLocked(..., { essentialsPublished })` now returns false when it is explicitly `false`; `undefined` keeps the old behaviour (older tokens self-correct on the next refresh). The flag comes from `hasPublishedEssentials()` (`src/lib/induction-essentials.ts`, 60s cache, **assumes true on a DB error** so a blink can't unlock the org) and rides the JWT beside `inductionStatus`, refreshed on the same 5-min cadence, because middleware is Edge and can't reach Prisma. Deliberately scoped to the UI LOCK: `assertUserCleared` (rostering/clock-in) is unchanged, so WWCC, policies and profile still gate real shifts.
- **Admin release valve**: `POST /api/induction/clear` (owner/head_office, reason required, audited as `induction.clear`) sets `cleared` outright, surfaced per-person on the `/onboarding` → Induction pipeline board, plus a **"Clear all N"** sweep (`{ all: true, reason }`) that excludes the caller and writes one audit row PER PERSON — a backfill against an empty curriculum locks an organisation at once, and one-at-a-time is a chore that gets abandoned halfway. It exists because `/signoff` only clears someone already at `awaiting_signoff` with every blocker met and `/override` grants a rostering window WITHOUT lifting locked-mode — so there was no way for leadership to release a stuck account at all.
- **Gate satisfiability is a hard invariant**: every blocker in `getInductionReadiness` must have a `href` pointing at a page the LOCKED user can reach AND that can actually resolve the blocker. Broken twice on 2026-08-25 — the WWCC blocker linked to `/profile`, which had no cert uploader (the uploader is on `/compliance`, which locked users were redirected away from), and the profile blocker demanded an emergency contact that only the admin `/staff/[id]` tab could add. Result: 0 of 82 staff could ever clear. `/profile` now carries both (`MyCertificatesSection`, `EmergencyContactsSection`). Before adding a blocker, verify a locked staff member can self-serve it end to end.
- **New-starter creation**: `POST /api/users` accepts `newStarter: true` + `startDate` → `inductionStatus: new_starter`. Default creation stays `cleared`.
- **Backfill**: `POST /api/induction/backfill` (owner/head_office) — enrols active cleared staff missing the essential track into it, `in_training` + 5-week (`35d`) grace. Idempotent; no-op if no essentials published.
- **Crons**: `/api/cron/training-monthly` (1st of month, enrols cleared users in that month's `TrainingCalendarSlot` courses, `"0 22 1 * *"`) and `/api/cron/induction-grace` (daily, expires grace windows, `"0 20 * * *"`).
- **Seed**: `prisma/seed-induction.ts` (called from `prisma/seed.ts`, idempotent) — 7 essential + 12 monthly courses as DRAFTS with placeholder content, 6 practical checklist items, 12 calendar slots. **Content is placeholder — real curriculum authored separately. Gate only counts `status: published` essential courses, so it stays inert until courses are published.**
- **Rollout**: (1) merge = no-op, all `cleared`; (2) publish essential courses one by one; (3) launch backfill; (4) grace expiry gates stragglers; (5) new hires use the "New starter" flag. Course track: `LMSCourse.track` = `essential | monthly | library`.

## Enrolment PDF (2026-09-17)
- **Never blank a section over one bad field.** `primaryParentSchema` fields were `z.string().optional()`, which accepts `undefined` but REJECTS `null` — one null `crn` failed the whole object, `parseJsonField` returned its `{firstName:"",surname:""}` fallback, and the pack printed an EMPTY "Primary Parent / Guardian" section while the dashboard (raw JSON) showed the family in full. Fields now use `parentText()` = `z.string().nullish().catch(undefined).transform(…).optional()` — a bad field degrades itself, never its siblings. Six other consumers read this schema (children list, new-family-welcome cron, enrol status, first-day-photo, relationships), so the fix is at the schema, not the call site.
- **`src/lib/enrolment-pdf.ts` reads parents via `parentRecord()`**, which keeps the parsed result only on success and otherwise falls back to the RAW object, coercing per field through `text()`. A pack that prints what it can beats one that silently prints nothing.
- **Both parent sections print the same fields** (address, occupation, workplace, work phone, CRN). The pack exists to be re-keyed into OWNA; a second parent recorded as a name and a mobile means ringing the family back.
- **`livesWithPrimary`** on the secondary parent is a FLAG, not a copied address — the PDF resolves the primary's address at render time, so correcting the primary's address later keeps them in step. The form ticks it instead of asking twice (`sharedAddress` prop on `ParentSection`); ticking clears any typed address so the record never holds two competing answers.
- **A red asterisk is not enforcement (2026-09-20).** The second parent's DOB had a field, a star and a PDF row, and nothing that made anyone fill it in: `dobRequired` only drew the star, and the wizard has NO `<form>` element, so the native `required` attribute never fires. `validateStep` in `src/components/enrol/types.ts` is the ONLY gate, and it asked for the second parent's name and mobile but not their DOB — so packs arrived blank in the field that most often sends one back to the family. `validateStep` now checks it in both branches (mandatory when `courtOrders === false`; consistency-checked when the family has begun filling the section). `dobRequired` is gone: the section's own `required` prop draws every star, driven by the SAME `secondaryParentStarted(sp)` helper `validateStep` uses, so markers and enforcement cannot drift. That helper tests every field, not just `firstName` — keying off the first name alone meant a parent who started with the surname saw no markers and then hit a wall on Next. **When adding a required enrolment field, add it to `validateStep`; marking the input is decoration.**

## Parent enrolment: Next must never be a dead end (2026-09-22)
- **The bug parents reported as "the Next button doesn't work".** `/parent/enrol` rendered Next as `disabled={!canAdvance}` and put the reason (`stepBlocker`) at the BOTTOM of the step. The nav is `sticky bottom-0` on mobile and static on desktop — so on a phone Next stayed pinned in the viewport while the explanation sat below the fold. Measured on a 390x844 screen at step 0: Next at y=783, "Please enter your CRN" at y=1575, page height 1839. A parent taps a greyed-out button, gets no feedback whatsoever, and concludes it is broken. It never showed up in testing because on desktop the message sits directly above the nav.
- **Next is now never disabled.** `handleNext` advances when `stepComplete`, and otherwise calls `showBlocker()` — which scrolls the banner into view (`block: "center"`, so the fields it names stay above it) and rings it. The banner is `role="alert" aria-live="assertive"` with `id="enrol-blocker"`, and Next carries `aria-describedby` pointing at it. Submit is the same: genuinely disabled only while a request is in flight. **Never re-add `disabled` to these buttons — dimming (`opacity-60`) signals "not finished" without removing the only way to find out why.**
- **`stepBlocker` is therefore load-bearing**: a `stepComplete` rule with no matching message returns Next to doing nothing. `src/__tests__/lib/enrol-blocker-never-silent.test.ts` walks every step from empty to complete and fails if any incomplete state yields a null/blank blocker (and self-checks that each ladder actually ends complete, so the assertions can't pass vacuously). `showBlocker()` also falls back to a toast rather than silence. **Adding a completeness rule means adding its message.**

## Parent Account Recovery (2026-09-18)
- **The portal had no password reset at all.** `ParentAccount.passwordHash` was written exactly once, at sign-up, by `createParentAccount` and by nothing else. "Forgot your password?" sent a magic LOGIN link (`/api/parent/auth/send-link`) — it signs the parent in and leaves the forgotten password in place, so the next sign-in fails identically; the sign-up route meanwhile told people they could "reset your password from the sign-in page".
- **Now**: `ParentPasswordReset` (mirrors `ParentMagicLink`; separate model on purpose — different lifetime, different blast radius, invalidated independently) + `src/lib/parent-password-reset.ts`. `POST /api/parent/auth/forgot-password` (public, always 200 — never reveals whether an address has an account; silent for a deactivated family), `GET/POST /api/parent/auth/reset-password` (GET CHECKS a token without consuming it so `/parent/reset-password` can say "expired" BEFORE the parent types a password), page at `/parent/reset-password`. Completing a reset claims the token with a guarded `updateMany`, kills every other outstanding reset for that address, and stamps `emailVerifiedAt`. It deliberately does NOT sign them in.
- **Link TTL is 1 hour**, resets and magic links alike (was 15 min). Parents ask at pick-up and read the email that evening; the old window guaranteed a dead link, and "the link doesn't work" is the report you get.
- **`?error=expired` is now rendered.** `/api/parent/auth/verify` had always redirected there and the login page never read it — the parent landed on a blank sign-in form with no explanation. `LoginNotice` handles `error=expired` and `reset=1`.
- **Staff side**: `POST /api/families/[id]/access` with `action: send_reset | send_login | set_password`, surfaced as `FamilyAccessPanel` on the family detail page. `set_password` is owner/admin ONLY, audited as `parent_password_set` (the password itself is never logged) and burns outstanding reset links. Every action refuses while portal access is switched off, and unlike the public routes these REPORT send failures — staff are on the phone telling a parent to check their inbox.
- **Email bypass allowlist**: recovery mail sends through Resend directly, bypassing `EmailSuppression` — a months-old bounce must not cost a family access to their own account. `src/__tests__/lib/email-bypass-guard.test.ts` enumerates the four allowed files; adding one is a deliberate decision, not a way around the guard.

## File Uploads
- **Always use `uploadFileSmart(file)` from `@/lib/upload-client`** — never a raw `fetch("/api/upload")`. It downscales photos in-browser, then routes by size.
- **Why**: Vercel rejects a serverless request body over ~4.5MB at the edge, before the route runs. `/api/upload` advertised 10MB, so everything in the gap came back as a bare `413` with no server log. This made the staff WWCC uploader unusable and was a direct cause of the 2026-08-25 induction lockout.
- **Routing**: `<= SERVERLESS_BODY_LIMIT` (4MB) → `/api/upload` (magic-byte sniffed server-side). Above it → direct PUT to Vercel Blob via `/api/upload/blob-token`, then `/api/upload/verify` range-reads the stored object, re-runs `validateFileContent`, and **deletes the blob** if the bytes contradict the declared type. Never persist a direct-upload URL before verify returns ok.
- **Shared constants** live in `src/lib/upload-strategy.ts` (`UPLOAD_ALLOWED_MIMES`, `SERVERLESS_BODY_LIMIT`, `ABSOLUTE_MAX_UPLOAD`). Adding a MIME there means also adding its magic-byte signature to `detectFileType` in `src/lib/file-validation.ts`, or the type is accepted by the allow-list and then rejected by the sniffer.

## Amana AI knowledge store (2026-09-27)
- **Opt-in by adapter.** `KnowledgeSource`/`KnowledgeChunk` are written ONLY by `src/lib/knowledge/pipeline.ts` (`upsertKnowledgeSource` → `indexSource` → `applySupersession`; `excludeSources()` is the one writer of `status: "excluded"`), fed by `src/lib/knowledge/adapters/*` — the eight `KnowledgeSourceKind`s: `sharepoint`, `policy_upload`, `help_article` (staff `KnowledgeBaseArticle`, i.e. `/help` — NOT the parent Help Centre), `handbook`, `lms_module` (published courses only), `centre_facts`, `regulator`, `manual`. There is deliberately NO path from a `Document` row into the store — the HR file cabinet (233 contracts) must never be indexable. `src/__tests__/lib/knowledge-guard.test.ts` enforces it (plus: no `/api/knowledge/*`, no store-wide `reindex`/`backfill`/`dedupe` routes, `document-indexer` exports no storage/search, the tools list has `search_knowledge` and no `search_knowledge_base`, the SharePoint PII floor, and the single `excluded` writer). `/knowledge` is a bare redirect to `/assistant` and its nav item is gone.
- **Scope is SQL.** `searchKnowledge(query, scope, limit)` takes `buildKnowledgeScope(session)` (`{ role, serviceIds, state }` from `getCentreScope` + `canonicalState`) and filters `status='active'`, `serviceId`, `state` and `audienceRoles` in the `WHERE` — the model never sees scope parameters. Hybrid tsvector ⊕ pgvector (Voyage `voyage-3`, 1024-dim, `VOYAGE_API_KEY`; the fetch has a 30 s `AbortSignal.timeout`), RRF-fused (k=60). `fusedScore` orders; `cosineDistance`/`tsRank` are the relevance signals (slice-2 thresholds use those, never RRF). Without `VOYAGE_API_KEY` sources index tsvector-only with `embedded: false` and NO `indexError` — degraded is not failed (the console shows a "Keyword-only" chip + a banner when the key is unset; the Errors tile counts `indexError` only). `KnowledgeSource.text` is the canonical source text (routes cap at 500KB): rename-only edits, `[id]` GET (`body`) and `[id]/reindex` read it — chunks are NEVER rejoined. The upsert writes `text`/`contentHash` with `indexedAt: null, embedded: false` BEFORE indexing and only a successful `indexSource` stamps `indexedAt` + `embedded` (and clears `indexError`); the "unchanged" fast-path needs `contentHash` match AND `indexedAt != null` AND `indexError == null` AND (`embedded` OR no key configured) — so a crashed index and a keyword-only row are retried on the NEXT sync once the key exists, but nothing is re-chunked every sync while there is no key. `text === ""` (rows from before the column existed) also re-indexes.
- **Dedupe key** is `(normalizedTitle, state, serviceId)`. Within a key exactly one row is `active`: `KIND_PRIORITY` `policy_upload` > `manual` > `sharepoint` > others, then `CATEGORY_PRIORITY` `policy` > `procedure` > `sop` > others (owner rule 2026-09-26: the Jayden SOP set is over a year old and must NEVER supersede the actual state policies — a policy/procedure beats an SOP of the same title whatever its version or recency), then highest `version`, then most recently updated; losers are `superseded` (+`supersededById`), `excluded` rows are never touched, and a group left with only superseded rows promotes its best one back. Same-version-different-content = a CONFLICT in the sync report for Daniel to fix in SharePoint, never auto-picked. A rename-only edit (hash unchanged, title changed) persists via the upsert fast-path and re-runs supersession for the OLD and NEW key; the admin status/delete writes re-run it for the row's key, and `excludeSources` re-runs it for every group it touched (keys are read BEFORE the flip) — an excluded row that was the group's winner would otherwise leave the real document `superseded` with no active row. `excludeSources(where, by)` records `excludedBy` so an adapter can undo only its own exclusions and never overwrites an admin's. The `tier` column is ALWAYS `inferTier`'s heuristic — adapters do not force it; the one exception is `centre_facts`, which passes `tier: "general"` explicitly because a fact sheet is never a procedure whatever the centre is called. `inferTier` takes the `category` and returns `general` for every `sop` regardless of title (a stale SOP must never be quoted verbatim as the safety-critical authority — "OPS-08 Medical Administration" is `general`, "QA2 Managing Medical Conditions Procedure" is `safety_critical`; an admin `tierOverride` still wins). The upsert fast-path (hash unchanged) also lands a drifted `tier`/`category` without re-indexing, and `importExportDir` re-runs `applySupersession` for every dedupe key it saw after the walk — otherwise neither rule change reaches rows whose text did not change (an "unchanged" upsert never runs supersession). Retrieval mirrors the rule: `formatHitsForPrompt` labels every hit with its category and appends `SOP_HIT_NOTE` to `sop` hits, and the chat system prompt + `search_knowledge` description tell the model to prefer `policy`/`procedure` over `sop` for children's safety, compliance and regulations (SOPs are for company-internal process: finance, HR admin, growth).
- **Console** at `/settings/ai-knowledge` (owner/head_office/admin; page split into `src/components/settings/ai-knowledge/*` — `EntryModal`, `KnowledgeSourceRow`, `LastSyncPanel`). Routes under `/api/settings/ai-knowledge`: list/create (an explicit `tier` on create lands in `tierOverride` — the `tier` column is ALWAYS the heuristic; a failed override stamp reports in the body, never 500s, so the client can't retry into a duplicate), `[id]` (PATCH `title`/`body`/`tierOverride`/`status`, DELETE + blob), `[id]/reindex`, `upload` (Vercel Blob `handleUpload`; the `onUploadCompleted` webhook registers one source per file and one per entry for a `.zip`), `register` (idempotent: `externalId = uploadExternalId(blobUrl)` = `manual:upload:<blob pathname>` — the SAME id the webhook used, so register-after-webhook is a hash "unchanged", never a duplicate; zips short-circuit here because the webhook owns them), `sync` (GET latest run per adapter; POST `{ adapter: backfill | regulator }` = `RUNNABLE_ADAPTERS`), `seed` (handbook).

## API Versioning (Cowork)
- **Strategy**: URL path versioning (`/api/cowork/v2/...`) for breaking changes only
- **Current versions**: v1 (implicit, `/api/cowork/...`), v2 (`/api/cowork/v2/announcements` only)
- **Version header**: All cowork responses include `X-API-Version: 1` (or `2` for v2 routes). Clients can check this for compatibility.
- **When to create v2**: Only when a breaking change is needed (field removal, type change, response structure change). Additive changes (new optional fields) stay in v1.
- **Deprecation**: When v2 of a route exists, v1 responses include `X-API-Deprecated: true` and `Sunset` headers. Allow 90-day migration window before removing v1.
- **v2 conventions**: v2 routes use the canonical dashboard models (e.g., `Announcement` not `CoworkAnnouncement`), include activity logging, and resolve service by code.
- **New route checklist**: auth via `authenticateCowork()`, Zod validation, `withApiHandler()` wrapper, version header in response

## Rate Limiting
- **Authenticated routes** (`withApiAuth`): 60 req/min per user per endpoint. Override per-route: `withApiAuth(handler, { rateLimit: { max: 10, windowMs: 30000 } })`. Disable: `{ rateLimit: false }`.
- **Cowork routes** (`authenticateCowork`): 10 req/15min per IP for auth failures.
- **API key routes**: 100 req/min per key.
- **Login/password reset**: 5 attempts/15min per IP.
- **Backend**: Upstash Redis in production (`UPSTASH_REDIS_REST_URL` + `UPSTASH_REDIS_REST_TOKEN`). In-memory fallback when env vars not set (dev only).
- **Rate limit key format**: `auth:{userId}:{pathname}` — per-endpoint to prevent false 429s when dashboard loads multiple APIs in parallel.

## Auth Event Logging
- All auth rejection paths in `withApiAuth` log structured warnings via `logger.warn()`:
  - `Auth: no session` — unauthenticated request
  - `Auth: deactivated user` — user account disabled (includes userId)
  - `Auth: role denied` — role not in allowed list (includes role, required roles, endpoint)
  - `Auth: below minRole` — role below minimum required
  - `Auth: feature denied` — feature check failed
  - `Auth: rate limited` — rate limit exceeded (includes userId, endpoint, resetIn)
- Request IDs (`x-request-id` header) are set on all responses from `withApiAuth` and `withApiHandler` for log correlation.

## Error Handling
- **Server routes**: Throw `ApiError` from `@/lib/api-error` inside `withApiHandler()` or `withApiAuth()` wrappers. Errors are formatted as `{ error: string, details?: unknown }`.
- **JSON body parsing**: Use `parseJsonBody(req)` instead of raw `req.json()` — returns 400 on malformed JSON, not 500.
- **Client hooks**: All mutations use `onError` with `toast({ variant: "destructive", description: err.message })`. All queries use `retry: 2`.
- **Client fetch**: `fetchApi<T>(url)` and `mutateApi<T>(url, { method, body })` from `@/lib/fetch-api` — includes timeout (30s default), error context (status, URL, server message), content-type validation.

## Enrolments list: reachable beyond page one (2026-09-20)
- **Nothing was ever lost — it just couldn't be asked for.** `/enrolments` fetched a fixed `limit=100` slice (newest first) with NO pagination, and the search box filtered *that slice in the browser*. Past 100 submissions the older forms were unreachable AND unfindable: typing a family's name returned "No enrolments match your search", which reads as data loss rather than "it's further down". The status-tab counts had the same shape of bug — computed from the loaded page, so "Submitted 12" meant twelve *on this page*.
- **Now**: `GET /api/enrolments` takes `search`, `limit` (default 50, clamped to 200) and `offset`, and returns `{ submissions, total, counts, unplaced, limit, offset }`. `counts` comes from a `groupBy` over `base` — the scope + search where WITHOUT the status tab — because a per-tab count must describe the whole set, not the open tab. `unplaced` excludes `archived` (a banner that can never reach zero stops being read).
- **Search is SQL** (`src/lib/enrolment-search.ts`), not a Prisma JSON filter: parent names live in `primaryParent` JSONB but child names live inside the `children` ARRAY, which Prisma's `path`/`string_contains` cannot reach — and staff search by the child at least as often as the parent. LIKE metacharacters are escaped (`likePattern`), `jsonb_typeof(children) = 'array'` guards malformed rows, and the candidate set is capped at `ENROLMENT_SEARCH_CAP`. The `serviceId` argument narrows the scan; it is NOT the authorization boundary — the route still intersects the returned ids with `serviceScopeFilter(session)` in Prisma.
- **Client**: `useEnrolments(status, search)` is a `useInfiniteQuery` (`ENROLMENTS_PAGE_SIZE` 50) with "Load more" and a "Showing X of Y" line; rows are deduped by id because offset paging can repeat a row when one arrives mid-scroll. Never re-filter the list in the page component — that is the original bug. Search is debounced via `useDebouncedValue`.
- **CSV export walks every page** (`fetchAllEnrolments`) instead of writing out the loaded rows. A silently truncated export is worse than none when it is being reconciled against OWNA.
