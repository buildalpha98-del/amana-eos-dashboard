# Invoice delivery recovery

User approved this scope on 10 October 2026: persistent PDF/email state, transient retries and an admin retry action, using existing infrastructure, isolated tests and a reviewed PR. Merge and production release are separate.

Each newly issued statement gets one delivery row in the same database transaction. Existing invoices stay untracked; there is no backfill or mass resend. A shared worker runs immediately through runAfter, from a bounded cron batch, or after an authorized retry. Conditional leases and tokens fence every database checkpoint. PDF upload is separate from persistence; the winning worker atomically records the PDF URL on both delivery and statement. Email payload is escaped, frozen and encrypted with the existing field key before first send.

Resend accepts stable idempotency keys for 24 hours with an identical payload ([provider documentation](https://resend.com/changelog/idempotency-keys)). Retries retain the exact payload, key and first-send timestamp. A conservative 23-hour window bounds recovery after an uncertain acceptance; expired uncertainty requires provider reconciliation, never a blind resend. Success means provider acceptance with a message ID, not delivery to the inbox. Suppression, missing recipient and configuration problems surface separately from transient failures. No new provider or queue dependency.

The existing statement detail panel shows pending, processing, sent to provider, failed, blocked or needs review. Only existing admin roles can request a safe retry, and the new mutation checks Origin locally. Draft/void invoices cannot be delivered or revived. Paid/overdue descendants of an issued invoice remain eligible. Work already accepted by a provider cannot be recalled by a subsequent void.

Acceptance: issue/job atomicity; simultaneous issue and worker-claim safety; crash recovery and stale-worker fencing including PDF persistence; immutable payload after contact/config changes; provider acceptance surviving a logging failure; bounded retries without timestamp reset; suppression/deadline/void behavior; retry authorization and same-origin enforcement; accessible loading, disabled, success and error UI. Validate with local PostgreSQL, meaningful unit tests, isolated synthetic preview and independent review. No real recipient or production data mutations during verification.

Independent design review by invoice_recovery_design_review identified PDF checkpoint fencing, absent existing CSRF checks and ambiguous provider success; all are explicit implementation requirements. Existing public PDF storage is inherited and outside this recovery change. General notification refactoring, overdue/payment delivery recovery, historical resend and test TypeScript cleanup are excluded.

Implementation and pre-preview verification: one unique delivery row is created atomically with issue; worker, bounded cron and same-origin admin retry share fenced state. The API exposes an explicit safe summary only. Existing provider/PDF helpers are reused; recoverable logs omit recipient, subject, body and PDF URL.
